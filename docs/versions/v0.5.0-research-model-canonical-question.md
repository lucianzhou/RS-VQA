## 1. 版本目标

修复一个会让中文用户完全误判模型能力的严重缺陷，并把“问题规范化”从隐式关键词规则升级为
**可追溯、可核验、可拒答**的受控契约。

本版不做：不训练、不微调、不换 checkpoint、不改 `rs-vqa-fusion` 研究代码、不动答案排序、
不加答案类型 hard mask。

## 2. 缺陷

`services/model-service/app/question_matcher.py` 早已能把中文口语问题规范化成英文
canonical question，但 `app/main.py` 在 REAL 路径调用的是：

```python
ResearchRuntimeBackend.predict(raw, question)   # question = 用户原始中文
```

canonical question 被算出来却**只用于展示**，从未送进模型。冻结的 ViLT 分类器主要基于英文
RSVQA-HR 模板训练，中文直传导致答案与模型自己预测的题型互相矛盾。

真实 CPU runtime 实测（`data/test-images/single/san_francisco_coastal_urban.jpg`）：

| 输入 | 原始预测 | 置信度 | 预测题型 |
| --- | --- | ---: | --- |
| `有几条路？` | `no` | 0.6886 | count |
| `图中有没有道路？` | `no` | 0.4840 | count |
| `Is there a road?` | `yes` | 0.8523 | presence |
| `What is the amount of roads?` | `1` | 0.3905 | count |

`count` 题型返回 `no` 是形态自相矛盾的输出，说明中文输入实际落在训练分布之外。

## 3. 修复

### 3.1 REAL 路径只接受 canonical question

```python
model_input = match.canonical_question
if not model_input:
    raise HTTPException(status_code=503, detail="规范化问题缺失，拒绝以原始文本调用研究模型。")
result = _load_research_backend(RELEASE_MANIFEST_PATH).predict(raw, model_input)
```

canonical 缺失时**宁可 fail-closed 也不回退到原文**。

### 3.2 受控词表结构

原实现是一组扁平别名 + 关键词判断，隐式允许“任意对象 × 任意题型”。现拆为：

- `app/question_catalog.py`：纯数据（intent、地物、支持矩阵、canonical 模板、触发词、诱导词）；
- `app/question_matcher.py`：跨度最长优先的匹配逻辑；
- `app/answer_display.py`：仅展示的本地化渲染。

完整契约见 [`docs/architecture/model-input-normalization-contract.md`](../architecture/model-input-normalization-contract.md)。

### 3.3 canonical 模板全部换成 RSVQA-HR 已证实句式

四个模板均可在与本 release 绑定的证据中逐字找到：

| 题型 | Canonical | 证据 |
| --- | --- | --- |
| presence | `Is there a {singular}?` | 发布 wheel warmup + RSVQA-LR 问题集 |
| count | `What is the amount of {plural}?` | `docs/16_predicted_soft_case_audit.md`、`thesis/experiment_materials.md`、release smoke |
| area | `What is the area covered by {plural}?` | `docs/16_predicted_soft_case_audit.md` |
| comparison | `Are there more {plural} than {other_plural}?` | `docs/16_predicted_soft_case_audit.md` |

count 模板由 `How many X are there?`（仅 RSVQA-LR 证据）改为 HR 已证实的
`What is the amount of X?`。真实模型上该形式对同一图像给出更高 margin
（roads：0.107 vs 0.008）。

### 3.4 中文口语别名

新增 `房子`、`房屋`、`楼`、`民房`、`街道`、`路`、`条路`、`停车位`、`小区`、`农地`、`树林`、
`草坪` 等。`路有几条`、`多少条路`、`几个停车场`、`停车场有几个` 均可映射。

短别名（`路`、`楼`）通过 `DecoyTerm` 防止误匹配：`思路`、`线路`、`路口`、`楼层` 等长词先占位。

### 3.5 拒答与澄清

| 场景 | 行为 |
| --- | --- |
| `住宅`（可指住宅建筑或住宅区） | 澄清，返回两个候选 |
| `图中有多少建筑物和道路？` | 澄清，一次只答一个地物 |
| `铁路 / 机场 / 桥梁` | 拒答，明确不在词表 |
| `学校 / 操场 / 施工区域 / 工业区` | 拒答，指名“尚未核验” |
| `道路的覆盖面积` | 拒答，线状要素无面积档位证据 |
| `建筑物比道路少吗？` | 澄清，canonical 只表达 “more”，改写会反转语义 |
| `图中不存在道路吗？` | 不匹配，要求改写，避免 yes/no 反转 |
| `图中几乎都是道路` | `几乎` 不算 `几`，不误判为计数 |

澄清场景 `status` 仍为 `unsupported`（确实没产生答案），由 `needs_clarification` 与
`reason_code` 承载区分。这样刻意避免了新增状态值在 `AnalyticsService`、`BatchService`、
`TrustedAgentTools`、`ReportService` 里造成的**统计空洞**——那些计数器按状态字符串分桶，
新状态会既不计入 answered、也不计入 unsupported/failed。

### 3.6 收紧“任意对象 × 任意题型”（原任务第 10 条）

已收紧 4 类组合，待核验项已逐条记录在契约文档第 5 节。核心判据：

- 面积答案是平方米区间，线状/点状要素（道路、行人）没有多边形面积证据 → 拒答；
- 学校/操场/施工区域/工业区在 HR 与 LR 证据中均未出现 → 移出词表并指名拒答；
- 其余组合一律标记 `provisional`，并在响应 `limitations` 中显式声明，不假装已验证。

### 3.7 原始答案与展示答案分离

- 数据库、审计、报告、`MessageEntity.content` 一律存原始预测（`3`、`no`、`0m2`）；
- `display_answer` 仅用于渲染（`3 条道路`、`是，图中存在道路`、`建筑物覆盖面积约 0 平方米`）；
- 前端 `.answer-value` 承载原始预测，`.answer-display` 承载本地化渲染；
- **答案形态与预测题型不符时不生成 display 文本**，改为 `answer_shape_mismatch=true` 提示复核。
  绝不把 `no` 改写成 `3`。

UI 顶部加一行轻量提示：`已理解为：图中有多少条道路？`，仅在问题被改写时出现。

## 4. 接口变化

`PredictionResponse` 新增 14 个字段（`original_question`、`canonical_question_display`、
`model_input_question`、`question_normalizer_version`、`matched_intent`、`matched_objects`、
`question_scope_verification`、`reason_code`、`needs_clarification`、`clarification_options`、
`interpretation_note`、`display_answer`、`display_locale`、`answer_shape_mismatch`）。

Gateway 侧：

- `ModelPredictionResponse` 增加对应 `@JsonProperty` 组件；
- `ApiPredictionResponse` 增加 `QuestionUnderstanding` 与 `AnswerPresentation` 两个嵌套记录，
  避免 34 个位置参数；`answer` 仍严格绑定原始 prediction；
- Flyway `V10__question_normalization_audit.sql` 为 `model_invocation` 增加 13 列；
- `ModelInvocationEntity.recordQuestionNormalization(...)` 是唯一写入口，外部 Provider 路径
  从不调用，因此“是否经过研究 canonicalizer”可直接从数据库判定。

### 顺带修复的边界缺陷

`WorkspaceService.askExternal` 原先把用户原文塞进 `canonicalQuestion` 槽位，使外部模型的回答
在 API 上看起来也“被规范化过”。现改为 `QuestionUnderstanding.notApplicable(question)`：
原文保留在 `originalQuestion`，canonical 相关字段全部为空。

`WorkspaceService` 的消息 metadata 原用 `Map.of(...)` 构建，遇 null 值会抛 NPE；新增字段大多可空，
已改为 `LinkedHashMap` + 条件写入。

| 层 | 结果 |

新增测试覆盖：

- 中文同义表达映射（房子/楼/房屋、几条路/多少条路/路有几条、几个停车场/停车场有几个）；
- 原始问题与 canonical question 双字段；
- **REAL backend 确实收到 canonical question 的回归测试**（记录后端实际入参）；
- 外部 Provider 不带 canonicalization（`QuestionUnderstanding.notApplicable`）；
- ambiguity / pending / blocked / 方向不支持 / 否定式；
- raw answer 与 display answer 分离，以及形态不符时不生成 display；
- provenance 字段与 Jackson 反序列化契约；
- 旧版 model-service 字段缺失时的降级；
- React：`已理解为` 提示、`.answer-value` 保持原始预测、澄清按钮回填输入框、provisional 提示。

**canonical 不动点测试**（`test_every_canonical_question_normalizes_to_itself`）在开发中抓到一个
真实缺陷：`Are there more A than B?` 因 `more than` 不是连续子串而被误判为 presence 问题，
导致英文 canonical 无法回流。已修复并固定。

## 6. 真实模型验收

`/ready` → `mode=real, ready=true, model_release_id=rsvqa-hr-qdrop15-predicted-soft-20260724-8510bc9`

`scripts/canonical_parity_smoke.py --mode all`（真实 CPU runtime，同一图像）：

| 题型 | 中文问题 | Canonical | 原始预测 | 展示 | 置信度 | scope |
| --- | --- | --- | --- | --- | ---: | --- |
| presence | `图中有没有道路？` | `Is there a road?` | `yes` | 是，图中存在道路 | 0.8523 | provisional |
| count | `有几条路？` | `What is the amount of roads?` | `1` | 1 条道路 | 0.3905 | release_anchored |
| area | `建筑物覆盖面积是多少？` | `What is the area covered by buildings?` | `0m2` | 建筑物覆盖面积约 0 平方米 | 0.9235 | provisional |
| comparison | `建筑物比道路多吗？` | `Are there more buildings than roads?` | `no` | 否，建筑物不多于道路 | 0.9709 | provisional |

两项 parity 均通过：

1. **语言 parity**：中文问题与英文 canonical 的原始预测、top-k 顺序与概率、题型概率、
   checkpoint/词表/runtime 哈希全部一致。
2. **运行时参考 parity**：HTTP 服务输出与直接调用 `rs_vqa.release_runtime` 的参考输出一致。

浮点容差 `1e-4`：同一输入重复 CPU 推理观测到约 `3e-6` 的漂移（PyTorch CPU 非确定性）。
原始预测、排序与哈希要求**完全相同**，只有概率允许该容差。

> `data/test-images` 是 USGS 工程测试影像，没有 RSVQA-HR 金标。以上结果只证明链路一致，
> **不能用于论证模型准确率**。

## 7. 能力边界（未变）

- RSVQA-HR grouped answer + ViLT closed-set 分类器，55 类固定词表；
- predicted-soft 部署只接受图像与问题文本，不读人工 `question_type_id`；
- 不是开放式 VQA，不接受 oracle / router / label mask / 评价 metadata；
- test OA/AA = 0.8401412 / 0.8390032，test_phili OA/AA = 0.8031558 / 0.7975786；
- **不声称 SOTA**，也不声称 predicted-soft 相对 none 显著提升（配对置信区间包含 0）。
